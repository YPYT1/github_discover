# 查看日志与排查访问故障

系统使用 Cloudflare 原生 Workers Logs，不另建访问日志数据库，不购买日志服务。

后续稳定运营补强已加入公共回源保护、采集进度和聚合告警；本地脱敏归档可用 `pnpm logs:archive`。配置与未启用项见[稳定运营与验收](稳定运营与验收.md)。下文的基础日志描述不代表外部报警已启用。

**限制先看**：免费套餐目前每天 20 万日志事件，保留 3 天（2026-10-09 官方规则）。本系统有聚合告警与本地有期限归档，但没有外部告警推送或无限永久归档。错误与慢请求在应用层不采样，但仍受平台额度、截断和进程终止限制；不能保证每次故障都有完整日志。日志不是高并发容量保证，也没有对生产做压力测试。

## 立即查看

在 Cloudflare 后台进入 **Workers & Pages → github-discover → Observability → Logs**。选择最近 15 分钟或故障对应时间。浏览器开发者工具的 Network 中，失败 API 响应的 `X-Request-ID` 可用于搜索本次请求的全部应用日志。

应用日志是结构化对象。优先筛选：

- `service`：`github-discover`。
- `level`：`error` 或 `warn`。
- `event`：`request.completed`、`application.error`、`dependency.completed`、`operation.failed`、`scheduled.failed`。
- `requestId`：某个失败响应的编号；编号每次请求由服务端生成，不接受浏览器指定。
- `route`：例如 `/api/feed`。仓库详情路径只记录 `/api/repositories/:owner/:name`，不记录真实仓库名。

在本地项目目录运行安全实时查看命令：

```powershell
pnpm logs
```

按 Ctrl+C 停止。需要只观察两分钟时：

```powershell
$env:LOG_TAIL_SECONDS='120'
pnpm logs
```

命令要求已登录 Cloudflare 或本机 `.env` 中有有效 Wrangler 权限。实时输出保留资源结果、固定路由、CPU/墙钟时间和安全应用字段；任意字符串日志、原始异常消息、请求头、Cookie 和查询参数不会转发。不要直接把未脱敏的 `wrangler tail --format json` 输出发给别人。

## 各类日志表示什么

- `request.completed`：HTTP 状态、`durationMs`、`githubRequests`、`cacheHits`、`cacheMisses`。`durationMs` 是到返回响应的墙钟耗时，不是 CPU 时间，也不是完整响应流传输时间。

  Workers 的计时器在纯计算阶段可能不推进；例如排序日志显示 `durationMs=0` 并不意味着没有 CPU 消耗。判断 CPU 开销必须结合平台原生 CPU 指标或安全实时命令的 `cpuMs`，不要仅凭应用阶段耗时做容量结论。
- `application.error`：安全错误分类，如 `d1Error`、`rateLimited`、`networkError`、`forbidden`。不保存原始错误堆栈或 SQL 参数；必要时用请求编号定位、在受控开发环境复现。
- `dependency.completed`：GitHub 接口分组、状态、收到响应头的耗时、`remaining` 剩余额度、`resetAt` 重置时间戳和 `retryAfter` 秒数（上游有提供时）。不包含 Token、实际仓库路径或搜索内容。
- `cache.lookup`：采样请求的缓存类型与命中结果。
- `operation.completed` / `operation.failed`：推荐排序、仓库缓存写入和 feed 阶段的耗时/失败分类。不是每一条 D1 SQL 的追踪。
- `scheduled.completed` / `scheduled.failed`：每六小时的采集任务结果；成功日志的 `relatedRequestId` 关联内部同步 API 的请求。查看“已经过去的应运行时刻”有无结果，而不是仅看 Cron 配置。

静态首页及静态资源绕过应用 Worker，因此没有每次首页访问的应用请求日志。这是刻意减少 CPU 和日志负担；API 有单独日志。浏览器脚本错误目前没有主动上传收集端；检查浏览器 Console。

## 遇到 1102 或页面被终止

查看 Cloudflare 原生 invocation/资源指标与实时命令的 `outcome`、`cpuMs`。`exceededCpu` 才是 CPU 超限证据；`canceled` 只是调用取消，不能据此判定数据库坏了。

CPU/内存超限可能直接终止进程，应用无法执行最后一条日志或返回自己的请求编号。此时记录 Cloudflare 页面上的 Ray ID、UTC 时间、API 路径，查看平台资源事件。不要把 API 的墙钟时间当成 CPU 时间。

## 遇到 429 或推荐数据变少

搜索 `errorCode=rateLimited` 和 `dependency=github`，检查 `remaining`、`resetAt`、`retryAfter`。多人冷请求、复杂多选筛选、Cron 和用户画像拉取都可能消耗 GitHub 配额。公共回源已增加请求合并和共享租约，但租约过期、多实例资源限制等仍需观察。

先等待配额恢复、检查共享缓存命中与运维状态。访问保护已加入轻量入口限流、公共回源合并与旧缓存降级；专用 GitHub 服务端采集 Token 仍需配置。用户 OAuth/PAT 与公共采集令牌的配额不是同一个概念。

## 遇到 D1 错误或读写变慢

搜索 `errorCode=d1Error`，并检查 `stage=repository_cache` 或 `/api/feed` 的操作耗时。到 Cloudflare 的 D1 数据库 Metrics 检查读写量、延迟和额度。推荐缓存、曝光保存和仓库快照都会产生写入；大量访问可能遇到每日额度、排队或延迟。

可识别的 D1 消息会进一步分类：`d1Schema`（表/列不存在）、`d1Quota`（配额）、`d1Busy`（繁忙/排队）；其余为 `d1Error`。这些只是安全模式匹配，不替代平台 Metrics 的判断。

日志没有逐条 SQL 或参数，不应据通用 500 提示立即重建数据库。先确认绑定/迁移、配额和对应请求编号。

## 日志过多或没有日志

`wrangler.jsonc` 中的 `LOG_SAMPLE_RATE` 默认 `"0.05"`：只对应用成功请求和其正常阶段日志做 5% 采样；4xx/5xx、依赖失败、超过两秒的阶段/请求以及 Cron 结果不按此比例丢弃。正常请求的一条日志都没有可能只是未被采样，不代表请求没发生。

Cloudflare `observability` 的平台 head sampling 与应用采样不同：目前保持平台默认全采集，以保留错误。不要为了压日志量直接降低平台采样后仍声称“所有错误完整保留”。原生 invocation 自身也占日志事件额度，大量错误/恶意请求可导致日志量上升。

本系统的应用日志禁止写入 Token、Cookie、搜索内容、用户资料、原始异常文本。**Cloudflare 原生 invocation 元数据仍可能含完整 URL（包括搜索或 OAuth 回调参数）**，不受应用字段脱敏函数控制；保留后台访问权限边界，只用安全命令分享诊断，勿公开导出原生日志。若要求全平台不留请求 URL，需要另行设计日志/原生 invocation 的取舍，不能承诺本次应用脱敏能替 Cloudflare 修改元数据。

## 流量增长后优先关注

1. Worker API CPU/内存及每日请求额度：本次日志不解除免费版限制。
2. GitHub 配额与超时：看 `dependency.completed`，减少并发重复回源。
3. D1 每日读写额度、队列和延迟：看应用失败分类结合 D1 Metrics。
4. 缓存命中下降与排序阶段耗时上升：看请求计数与 `operation.completed`。
5. Cron 执行失败或趋势基线停更：看 `scheduled.failed` 和快照日期。
6. 日志额度/保留时间：必要时人工导出脱敏数据，或另行确认长期归档和报警方案，不会自动购买服务。
